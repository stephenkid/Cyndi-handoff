## 一、结论摘要

1. **仓库 A 是一个"设计沙盒 + 新首页"，不是能替换线上站的新系统。** 里面只有公开首页（React 静态页，约 950 行，无后端、无 `functions/`、无 `migrations/`）和 7 份文档。门户（Portal）、库存、出库、积分全部只有文字。
2. **A 的定位是"在旁边先想清楚，再迁回线上"。** `docs/HANDOFF.md` 写明它与 `cyndi-global-website` 分开、同栈"便于迁移回线上"。实际上**迁移已经开始**：A 的首页已经被搬进 B 的 `product-showcase/src/cyndi/home/`（`content.js`、`SixSteps.jsx`、`Distribution.jsx`、`Faq.jsx` 与 A 逐字相同；`Hero.jsx` 有改动），B 的提交 `e3be64f`、`76dca91`、`dac0629`（11-24）与 A 的同名提交对应。所以 A 的首页文案（四种出库、OIDC SSO、多币种、DDP、200+ 国家）**已经在线上首页上**。
3. **仓库 A 的作者就是 B 里 Portal 的作者**（Georgiazhu / "Cyndi Global" 提交身份，由 AI 助手 WorkBuddy 写文档）。A 文档里的"客户"指 **Cyndi Global 公司本身**（WorkBuddy 的客户），不是 HRT。所以 `DECISIONS.md` 的"客户已拍板"是 Cyndi 内部的决定，**没有 HRT 的签字**。
4. **A 和我们的设计有 8 处实质冲突**，其中最要紧的两处：
   - 个人链接要不要审批：A 说每单都要客户管理员审批（Q3）；HRT 的 Megan 要求个人链接不用审批，我们的 rev4 也是这样设计的。**建议以 HRT 的要求为准**，把审批做成"按活动可配置"，个人链接默认关。
   - 身份系统：A 计划 OIDC SSO + RBAC + 审计；B 现在是 `customers` + `customer_session` cookie，Portal 还加了 viewer/senior。两边方向不矛盾，但 A 只写了一个客户角色 Client Admin，B 线上已有三种客户身份。
5. **库存口径其实基本一致。** A 的 `allocated` 就是我们的 `reserved`；A 自己的 `docs/PORTAL-IA.md` 也写了我们的库存"Matches Q1"。差别只在"审批型订单何时占库存"：A 是审批通过时，我们是提交时。
6. **A 有大量我们完全没设计的东西**（积分账户、账单/发票、多币种、DDP 关税、PDF、只读 API 与 webhook、OIDC、审计、商品池 Re-quote），合起来比我们当前的兑换设计大好几倍。
7. **建议：继续我们的计划，把它当作走向 A 的第一步，但先改三处让它和 A 对齐**（订单加 `channel` 字段、审批做成可配置、编号和命名对齐 M1–M4）。不建议停下来等 A，也不建议把设计整个改成 A，因为 A 没有代码、没有经过 HRT 确认。
8. **公开仓库 A 里没有密码或密钥**，但有不该公开的内部信息：D1 数据库 ID、个人 Gmail、内部推送技巧、"HRT/showcase" 客户名、承运商名称 Yanwen（与它自己的"品牌脱敏"规则冲突）。详见第九节。

## 十、结论和建议

### 总体判断

A 是 Cyndi 想要的"完整平台"的蓝图，方向和我们一致（同栈、复用 B 的表、租户隔离、统一订单表、提交即审批的公开门户）。它没有代码，部分决定没经过 HRT，有两条规则（个人链接强制审批、审批时才占库存）比我们的更差。我们的兑换和多客户设计可以看作 A 的 M3/M4 和租户隔离的第一版。

1. 我们的 rev4：给 `orders` 加 `channel` 列；`requires_approval` 改为"公开门户强制、个人链接可配置（默认关）"；把 `/api/showcase-admin/*` 考虑改为 `/api/client-admin/*`；在文档里加一张"我们的叫法 ↔ A 的叫法"对照表（reserved=allocated、A 型=M3、B 型=M4、Showcase admin=Client Admin）。

   - 把 Q3 改成"可配置，个人链接默认不审批"，并注明来源是 HRT；
   - 把 Q1 写清楚为"提交即占用"；
