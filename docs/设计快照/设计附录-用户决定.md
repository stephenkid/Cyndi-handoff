## 1. New architecture: three tiers, multi-client

- **Cyndi admin** (existing `/admin`, table `admin_users`): global owner view. Creates clients, assigns Showcase admins, sees every client's data.
- **Showcase admin** (NEW, lives in the `showcase/` app, separate repo): for a client's own administrators (first: Fei and Megan of HRT (their email addresses are omitted from this copy)). They sign in with their OWN Showcase customer account (own email each, not the shared HRT account) that carries a "Showcase admin" membership of a client. They are NOT in `admin_users` and must never reach `/api/admin/*`.
- **Storefront** (existing): the client's employees order.

Showcase admin v1 modules ONLY: Orders, Inventory, Redemption (portal management plus approvals). New server API namespace `/api/showcase-admin/*`; each endpoint verifies the customer session, the admin membership and the client scope server-side, and only returns that client's data. Reuse the existing business logic in `functions/_lib/*` (orders, inventory); do not duplicate it.

## 2. Multi-client from day one (HRT is client #1, but more clients will come)

- Add a `clients` table. HRT is the first row.
- Add `client_id` to ALL Showcase data and backfill every existing row to HRT: showcase products, orders/Showcase orders, inventory, order_stock_lines/movements as needed, customers' Showcase membership, and every new redemption table.
- **Product catalog is per client** (each client has its own products).
- **Inventory is per client** (each client has its own stock; inventory key becomes client + product + colour + size, or equivalent). Check how this interacts with `inventory.sku` being the primary key and the `UNIQUE (product_id, color_id, size)` constraint in `migrations/0013_inventory.sql` (already applied on remote D1, so the change must be a new migration, no editing 0013) and with `functions/_lib/inventory.js`.
- Every Showcase admin query is filtered by the caller's `client_id`; a client A admin must be unable to read or write client B data even with a guessed id. Add tests for cross-client denial.
- Appearance/branding per client: OUT of scope for now (single client today). Do not build it.
- Do not build a client-creation wizard UI now. A SQL/script path is enough.

## 3. Redemption portal consequences

- Every portal/batch belongs to a `client_id`. Management and approval screens live in Showcase admin, not Cyndi admin (Cyndi admin may get a read-only or global view, say which).
- Order numbers `RDM-...` must work everywhere orders are validated, including the local validator in `functions/api/admin/orders.js` and any in the Showcase admin orders API.
- Keep all earlier decisions: emails sent by the system for personal links, per-item quantity caps identical for both types, stock reserved at submission and released when an admin rejects a Type B order, Type B requires admin approval.

Commits c3c3943, 28a7a6f, 44f6370 (author "Cyndi Global", pulled in after the previous revision) changed `functions/api/admin/inventory.js` and `product-showcase/public/admin/inventory.html`. What they do (read the code, `git diff a449ef1 HEAD -- functions/api/admin/inventory.js`):
- `resetFromOrder` op (confirm `RESET-INVENTORY`): runs unconditional `DELETE FROM order_stock_lines`, `DELETE FROM inventory`, `DELETE FROM inventory_movements`, then seeds one tracked variant per line of one `SHOWCASE-yyyymmdd-nnn` order with available = line quantity.
- `ivwListStockSkus`: new flat `skus` list in the GET list response, `SELECT ... FROM inventory LEFT JOIN showcase_products`, no client filter; products with no inventory row are hidden from the list.
- The page now lists stocked SKUs per colour and, on opening one, shows only ordered colours.

Conflicts the design must resolve (give a concrete recommendation for each):
1. `client_id`: the unconditional DELETEs would wipe every client's stock/movements/reservations; `ivwListStockSkus` has no client filter and would leak other clients' stock. Specify how both are scoped by client (and restricted to the owner role in Cyndi admin), or removed.
2. Reuse: both functions live in the API file rather than `functions/_lib/inventory.js`. Specify moving the list logic to the lib so `/api/showcase-admin/*` can reuse it with a client filter.
3. Redemption reservations: a reset would delete in-flight `order_stock_lines` for pending redemption claims (Type B awaiting approval) and break the reserve/release invariant. Specify a guard: refuse while any open reservations exist, or never touch rows owned by non-seed orders.
4. Redemption item pool must come from the product catalogue, not from the stocked-SKU list (untracked products have no inventory row and are hidden there).
5. Migration 0014 changes inventory keys: list every query in the new code that must change (inventory columns, joins, the INSERT in the seed batch).
6. Order-number validation: `IVR_ORDER_RE` only accepts SHOWCASE-; state that RDM- orders are correctly NOT seed sources, and that the shared `isKnownOrderNo` from the earlier fix is still the only validator elsewhere.
