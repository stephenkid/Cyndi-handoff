# 广州仓 SKU 级库存管理 — 技术设计（仅设计，未改代码）

> 只读调查。除本文件外没有改动任何文件，没有提交，没有重启服务。
> 基线：主仓 `main@c83e979`；showcase 前端仓 `showcase/` `main@080ff4e`。
> 用户已锁定的决定（按 SKU、4 种数量、下单即预留、缺货拒单、后台手动维护、仅 Showcase、`shipped` 时扣减、`incoming` 命名）全部照办，本文不再讨论。

## 0. 结论先行

1. **最重要的发现：Showcase 订单根本不经过 `product_skus`。** Showcase 下单读的是 `showcase_products`（`migrations/0010_showcase.sql`），订单行快照是 `{productId, sku(款号, 如 T3265271), colorIndex, colorName, size, quantity, ...}`（`functions/api/showcase/orders.js` 的 `onRequestPost` 里 `snapshot.push(...)`）。`product_skus`（`0008_products.sql`，`CY-...-C01-M`）只属于公开商城（SW- 订单）。`.kiro/reports/gap-analysis-client-requirement.md` 第 40 行也写了两套目录"互不关联"。
   - 因为用户同时锁定了"按 SKU"和"只对 Showcase 生效"，库存 SKU 只能是 **Showcase 变体 = 商品 × 颜色 × 尺码**。本设计据此建表：`inventory.sku` 是一个不可变的库存 SKU 编码，并用 `(product_id, color_id, size)` 映射到 Showcase 变体。
   - 这只是对"按 SKU"的落地解释，四种数量、扣减时点等决定都没变。**请用户确认这一点**（§8 Q1）。
2. **Showcase 变体目前没有稳定身份。** 颜色只是 `colors_json` 数组里的 `{name, hex, image}`。订单行只记 `colorIndex`（数组下标）和 `colorName`。后台编辑器会删除颜色（`splice`），选色时还会自动改颜色名（`product-showcase/public/admin/showcase.html` `drawColors()` → `matchColourName`），保存时把颜色对象精简成 `{name,hex,image}`（同文件 `e_save` 处理函数）。下标和名称都不稳定。**前置改动：给每个颜色加一个稳定的 `id`**（§1.3）。这和 brief 提到的"颜色重建 DELETE"问题本质相同，只是发生在 Showcase 这一侧。`functions/api/admin/products.js` 里的 DELETE+重建只影响商城，库存不挂在 `product_skus` 上，所以它不会造成孤儿库存（§6.4 给出将来商城也要做库存时怎么改）。
3. **原子性方案：** D1 的 `db.batch()` 是一个 SQL 事务，某条语句**出错**就整批回滚；但**影响 0 行的 UPDATE 不算出错**，不会触发回滚（[Cloudflare D1 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/)，另见[实测文章](https://dev.to/hirodeath/zero-updated-rows-do-not-fail-a-d1-batch-testing-the-rollback-boundary-3odn)）。所以只靠"`WHERE available >= N` 加检查 `meta.changes`"做不到整单要么全扣、要么全不扣。本设计用**带名字的 CHECK 约束**（`available >= 0` 等）作为守卫：扣减语句不加库存条件，库存不够时 CHECK 报错，整批回滚，订单 INSERT 也一起回滚。另外下单前先读一次库存做预检，给用户友好的"only N left"提示；CHECK 负责兜住并发竞争。
4. **用一张"订单库存行"表 `order_stock_lines` 记录每单每个 SKU 预留了多少、当前状态（reserved/shipped/released）。** 取消、发货、回退都只按这张表操作，不再解析 `items_json`，所以天然幂等。改价重算（`showcase-order-pricing.js`）和订单改号都不会影响它。
5. **钩子位置：** Showcase 下单 POST → 预留；Showcase `{op:'cancel'}` → 释放；`functions/api/admin/orders.js` 改状态：→`cancelled` 释放，→`shipped` 扣 reserved，`shipped→processing` 回退。商城下单、商城改状态、商城取消都**完全走现有代码路径**，不碰库存。判断规则：变体有 `inventory` 行 = 计库存；没有 = 无限/按单生产。
6. **上线零风险：** 0013 只建新表。代码在表不存在或行不存在时都当作"不计库存"处理。上线第一天没有任何 SKU 有库存行，所以行为与今天完全一致。

## 1. 数据模型

### 1.1 现状证据

### 1.2 订单行怎样对应到库存 SKU（必须明确）

- **身份三元组：** `(product_id, color_id, size)`
  - `product_id` = `showcase_products.id`（不可改，见上表）。
  - `color_id` = `colors_json[colorIndex].id`（§1.3 新增的稳定 id）。商品没有颜色时取 `''`。
  - `size` = `sizes_json` 里的原文。商品没有尺码时取 `''`。
- **解析只在下单那一刻做一次，在服务端完成**，用的就是刚读出来的那行 `showcase_products`。解析结果写进两个地方：
  - `order_stock_lines(order_no, sku, qty)`：这是权威记录。之后的取消、发货、回退**只读这张表**，不再从 `items_json` 反推。
  - 快照行里新增一个 `stockSku` 字段（只用于展示和对账，可为 `null`）。快照其他字段保持不变。
- **同一订单里多行指向同一个库存 SKU**（客户端可以绕过购物车合并，直接发重复行）：按 sku 汇总数量，生成一条 `order_stock_lines`。
- **行没有对应的库存行**：这一行不计库存，跳过。订单其余部分照常处理。
- **商品计库存，但这一行缺颜色或尺码**：只要该商品有任何 `inventory` 行，同时商品有颜色却没选（`colorIndex` 为 null），或者有尺码却没选（`size` 为 null），就返回 400 "Please choose a colour/size for X"。不计库存的商品保持今天的行为（允许不选）。这是让计库存的商品能正确对上变体的最小规则。

### 1.3 前置改动：颜色稳定 id

- `colors_json` 里每个颜色加 `id`，格式为短随机串，例如 `c_k3x9q2`，满足 `/^[a-z0-9_]{1,24}$/`。
- `product-showcase/public/admin/showcase.html`：
  - `e_addcolor` 新建颜色时生成 `id`。
  - `e_save` 的 `colors.map(c=>({name,hex,image}))` 改成同时保留 `id`。
- `functions/api/admin/showcase.js` `saveProduct`：先读出旧的 `colors_json`，给传入的每个颜色定 id：
  1. 传了合法 `id` 就沿用；
  2. 没传时，找旧数据里 `name`+`hex` 完全相同的颜色，沿用它的 id（兼容浏览器里缓存的旧版编辑页）；
  3. 都没有就生成新 id。
- 读取接口 `functions/api/showcase.js` 和 `functions/api/admin/showcase.js` 的 GET 直接返回解析后的 `colors`，`id` 会自动带出去，不用改。
- 老数据回填：在"开始计库存"操作（§4 `track`）里先给该商品缺 id 的颜色补上 id 并写回 `colors_json`。不需要一次性全表迁移。

### 1.4 DDL：`migrations/0013_inventory.sql`

```sql
-- 0013_inventory.sql — 广州仓 SKU 级库存（单仓，仅 Showcase）。
-- 规则：某个 Showcase 变体（product × colour × size）在 inventory 里有行 = 计库存；没有行 = 不限量/按单生产（商城与旧行为不变）。
-- 单仓假设：唯一仓库是广州，因此不设 warehouse 列。扩展到多仓见设计文档 §1.6。
-- 只新建表，可重复执行（IF NOT EXISTS）。不要用 `wrangler d1 migrations apply --remote`（未跟踪的 0010_price_backup.sql 会被一起执行）。

CREATE TABLE IF NOT EXISTS inventory (
  sku                 TEXT PRIMARY KEY,               -- 库存 SKU 编码，创建后不可变（如 T3265271-BLACK-OS）
  product_id          TEXT NOT NULL,                  -- showcase_products.id（不设 FK：该表在部分环境由运行时 DDL 创建，且删商品不应级联删库存）
  color_id            TEXT NOT NULL DEFAULT '',       -- colors_json[i].id；无颜色 ''
  size                TEXT NOT NULL DEFAULT '',       -- sizes_json 原文；无尺码 ''
  available           INTEGER NOT NULL DEFAULT 0 CONSTRAINT inv_available_nonneg CHECK (available >= 0), -- 可售，前台显示 "N in stock"
  reserved            INTEGER NOT NULL DEFAULT 0 CONSTRAINT inv_reserved_nonneg  CHECK (reserved  >= 0), -- 已下单未发货
  incoming            INTEGER NOT NULL DEFAULT 0 CONSTRAINT inv_incoming_nonneg  CHECK (incoming  >= 0), -- 采购/补货在路上，未到仓（不在库）
  damaged             INTEGER NOT NULL DEFAULT 0 CONSTRAINT inv_damaged_nonneg   CHECK (damaged   >= 0), -- 残次，不可售
  low_stock_threshold INTEGER CONSTRAINT inv_threshold_nonneg CHECK (low_stock_threshold IS NULL OR low_stock_threshold >= 0),
  created_by          TEXT,
  created_at          TEXT NOT NULL,
  updated_at          TEXT NOT NULL,
  UNIQUE (product_id, color_id, size)
);
CREATE INDEX IF NOT EXISTS idx_inventory_product ON inventory(product_id);

-- 每单每个库存 SKU 的预留记录：取消/发货/回退的唯一依据（幂等）。
-- 不变量：inventory.reserved = SUM(qty) WHERE state = 'reserved'（按 sku）。
CREATE TABLE IF NOT EXISTS order_stock_lines (
  order_no   TEXT NOT NULL REFERENCES orders(order_no) ON UPDATE CASCADE ON DELETE CASCADE,
  sku        TEXT NOT NULL REFERENCES inventory(sku)   ON UPDATE CASCADE ON DELETE CASCADE,
  qty        INTEGER NOT NULL CONSTRAINT osl_qty_pos CHECK (qty > 0),
  state      TEXT NOT NULL DEFAULT 'reserved' CONSTRAINT osl_state CHECK (state IN ('reserved', 'shipped', 'released')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (order_no, sku)
);
CREATE INDEX IF NOT EXISTS idx_osl_sku_state ON order_stock_lines(sku, state);

-- 库存流水：一次事件一行，四个桶各记一个增量 + 事件后的余额。
-- sku / ref_order_no 不设 FK：取消计库存或删除订单后，流水仍保留作审计。
CREATE TABLE IF NOT EXISTS inventory_movements (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  sku             TEXT NOT NULL,
  type            TEXT NOT NULL,      -- track|untrack|stocktake|adjust|incoming|receive|damage|repair|writeoff|reserve|release|ship|unship|relink|threshold
  d_available     INTEGER NOT NULL DEFAULT 0,
  d_reserved      INTEGER NOT NULL DEFAULT 0,
  d_incoming      INTEGER NOT NULL DEFAULT 0,
  d_damaged       INTEGER NOT NULL DEFAULT 0,
  available_after INTEGER,
  reserved_after  INTEGER,
  incoming_after  INTEGER,
  damaged_after   INTEGER,
  reason          TEXT,               -- 后台操作必填（≤ 500 字符）；订单事件可空
  ref_order_no    TEXT,               -- 订单驱动的事件
  actor           TEXT NOT NULL,      -- 'admin:<username>' | 'customer:<id>' | 'system'
  created_at      TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_inv_mov_sku ON inventory_movements(sku, id);
CREATE INDEX IF NOT EXISTS idx_inv_mov_order ON inventory_movements(ref_order_no);
CREATE INDEX IF NOT EXISTS idx_inv_mov_created ON inventory_movements(created_at);
```

**设计说明**

- **为什么主键是不可变的 `sku` 编码，再加一个可改的三元组：** 如果后台改了尺码文字或颜色，可以把孤儿行"重新关联"（`relink`）到新变体，库存 SKU 编码和全部流水都保留。
  - 编码在 `track` 时生成：`{款号 或 product_id}-{颜色名 slug 或 color_id}-{尺码 slug 或 OS}`，转大写，只保留 `[A-Z0-9-]`，最长 64；重名时加 `-2`、`-3`。
- **为什么 CHECK 约束要起名：** 违反约束时报错文本是 `CHECK constraint failed: inv_available_nonneg`，代码可以据此区分"库存不足"和其他错误（§2.1）。这一点没能在线上 D1 实测，实施时要用本地 `wrangler pages dev` 验证报错文本（§7.4）。
- **实物在库：** = `available + reserved + damaged`，`incoming` 不算在库。这是计算列，不存（锁定决定）。
- **admin 永远不能直接写 `reserved`**，它只随订单变化。"把 available 设得比 reserved 还小"在这个模型里不会发生，因为两者是独立的桶。真正的风险是盘点数小于 `reserved + damaged`，§2.5 处理。

### 1.5 不变量与对账 SQL（实施时放进后台"对账"按钮）

```sql
SELECT i.sku, i.reserved, COALESCE(SUM(l.qty), 0) AS lines_reserved
FROM inventory i
LEFT JOIN order_stock_lines l ON l.sku = i.sku AND l.state = 'reserved'
GROUP BY i.sku
HAVING i.reserved <> COALESCE(SUM(l.qty), 0);
```

### 1.6 单仓假设与以后扩展到多仓

- 现在：唯一仓库是广州（HRT 文档 `.kiro/reports/hrt-redemption-portal-design-v1.md` 第 38 行"仅一个仓库"）。表里不设仓库列；后台页标题写"Guangzhou warehouse"。
- 以后扩展，不需要返工业务逻辑：
  1. 新迁移给 `inventory_movements` 和 `order_stock_lines` 加 `warehouse_id TEXT NOT NULL DEFAULT 'GZ'`。`ALTER ADD COLUMN` 成本很低。
  2. `inventory` 需要把主键改成 `(sku, warehouse_id)`。SQLite 只能"建新表 → 复制（填 'GZ'）→ 换名"。
  3. 所有库存 SQL 都集中在 `functions/_lib/inventory.js`（§3.1），改动范围只有这一个文件，加上下单时选仓的规则。
- 同理，如果以后货权按客户区分（HRT 的货寄存在 Cyndi 仓，gap-analysis 第 98 行），用同样方式加 `client_id` 维度。现在 Showcase 只有 HRT 一个客户（`0011_customer_showcase_access.sql`），不需要。

## 2. 原子操作 SQL（D1）

总原则：

- D1 没有跨 `await` 的事务。每个业务动作都**拼成一个 `db.batch([...])`**，在 D1 里它是单个 SQL 事务。
- 守卫用两种方式：
  - CHECK 约束（库存不能为负）：违反就报错，整批回滚；
  - `EXISTS (SELECT 1 FROM orders WHERE order_no=? AND status=?from)` 条件：状态已经变了，这批里所有语句都影响 0 行，自然什么也不改。
- 每批最后一条语句是改订单状态，沿用现有的 `WHERE status = ?from` 乐观锁。调用方看 `results[last].meta.changes` 判断是否成功，沿用现有的 409 逻辑。
- 守卫只看订单状态，而订单状态只在最后一条语句才改，所以整批里所有守卫看到的状态是一致的。

### 2.1 下单预留（`functions/api/showcase/orders.js` `onRequestPost`）

流程：

1. 现有的校验和定价逻辑不变。
2. 用已经读出的 products 解析每行的库存身份（§1.2），只针对有行的 SKU 查一次：`SELECT sku, product_id, color_id, size, available FROM inventory WHERE product_id IN (...)`。按 sku 汇总数量。
3. **预检：** 汇总后任一 sku 的 `需要数量 > available`，直接返回 409（§5.3 的结构）。
4. **没有计库存的行：** 走原来的 `insertOrder()`，逻辑完全不变。
5. **有计库存的行：** 一个 batch：

```sql
-- [0] 订单 INSERT（把 insertOrder 拆出 prepareInsertOrder，返回 statement + createdAt；insertOrder 内部改为调用它，商城不受影响）
INSERT INTO orders (order_no, customer_name, ..., items_json, item_count, total, status, created_at, status_updated_at, customer_id)
VALUES (?1, ..., 'pending', ?10, ?10, ?11);

-- 对每个 sku 依次加三条（?1 sku, ?2 qty, ?3 now, ?4 order_no, ?5 actor 'customer:<id>'）
UPDATE inventory SET available = available - ?2, reserved = reserved + ?2, updated_at = ?3
WHERE sku = ?1;                                   -- 故意不加 available >= ?2：不足时由 CHECK inv_available_nonneg 报错，整批回滚

INSERT INTO order_stock_lines (order_no, sku, qty, state, created_at, updated_at)
VALUES (?4, ?1, ?2, 'reserved', ?3, ?3);          -- FK：库存行在预检后被删掉 -> FOREIGN KEY 报错 -> 整批回滚

INSERT INTO inventory_movements (sku, type, d_available, d_reserved,
       available_after, reserved_after, incoming_after, damaged_after, ref_order_no, actor, created_at)
SELECT sku, 'reserve', -?2, ?2, available, reserved, incoming, damaged, ?4, ?5, ?3
FROM inventory WHERE sku = ?1;
```

- **断言：** 每条 inventory UPDATE 的 `meta.changes === 1`。理论上不会出现 0，因为行不存在时 FK 已经让整批失败。万一出现 0，记 error 日志。
- **错误映射：**
  - 报错文本含 `inv_available_nonneg`：重新读这些 sku 的 `available`，返回 409 `INSUFFICIENT_STOCK`。
  - 含 `FOREIGN KEY`：返回 409 "Stock for an item just changed, please review your cart"。
  - 含 `UNIQUE constraint failed: orders.order_no`：这是 `sgonNextShowcaseOrderNo` 本来就有的竞态。整批已回滚、没有扣库存；建议重新取号重试 1 次，否则返回 500，与今天一致。
  - 其他错误：500 "Could not place order"，与今天一致。
- **数量上限：** `MAX_LINES = 100` 时最多 1 + 3×100 = 301 条语句，在 D1 单批语句数上限内（上限值以 Cloudflare 文档为准，实施时核对）。
- **为什么不能部分扣减：** 订单和所有 sku 的扣减在同一个事务里，任一条失败全部回滚。不存在"扣了一部分行"或"扣了库存却没有订单"的状态。

### 2.2 取消释放（客户 `{op:'cancel'}` 和后台改为 `cancelled` 共用）

参数：`?1 order_no`，`?2 now`，`?3 actor`，`?4.. 允许的 from 状态`（客户用 `CUSTOMER_CANCELLABLE_STATUSES`；后台用确切的 `from`）。下面的 `G` 指订单守卫，客户路径额外带 `customer_id`：

```sql
-- G := EXISTS (SELECT 1 FROM orders WHERE order_no = ?1 AND <原有条件：customer_id / SHOWCASE_ORDERS_WHERE> AND status IN (...))
UPDATE inventory
SET reserved  = reserved  - (SELECT l.qty FROM order_stock_lines l WHERE l.order_no = ?1 AND l.sku = inventory.sku AND l.state = 'reserved'),
    available = available + (SELECT l.qty FROM order_stock_lines l WHERE l.order_no = ?1 AND l.sku = inventory.sku AND l.state = 'reserved'),
    updated_at = ?2
WHERE sku IN (SELECT sku FROM order_stock_lines WHERE order_no = ?1 AND state = 'reserved') AND G;

INSERT INTO inventory_movements (sku, type, d_available, d_reserved, available_after, reserved_after, incoming_after, damaged_after, ref_order_no, actor, created_at)
SELECT i.sku, 'release', l.qty, -l.qty, i.available, i.reserved, i.incoming, i.damaged, ?1, ?3, ?2
FROM order_stock_lines l JOIN inventory i ON i.sku = l.sku
WHERE l.order_no = ?1 AND l.state = 'reserved' AND G;

UPDATE order_stock_lines SET state = 'released', updated_at = ?2
WHERE order_no = ?1 AND state = 'reserved' AND G;

-- 最后：现有的订单 UPDATE 原样保留（客户路径即 cancelOwnOrder 里那条）
UPDATE orders SET status = 'cancelled', status_updated_at = ?2 WHERE order_no = ?1 AND ... AND status IN (...);
```

- 没有 `order_stock_lines` 的订单（旧订单、全部不计库存的订单）：前三条都影响 0 行，行为与今天一样。
- 重复取消：状态已经是 `cancelled`，守卫 `G` 不成立，不会重复释放。

### 2.3 发货扣减（后台把状态改为 `shipped`）

```sql
-- G := EXISTS (SELECT 1 FROM orders WHERE order_no = ?1 AND status = ?4 /*from*/)
UPDATE inventory
SET reserved = reserved - (SELECT l.qty FROM order_stock_lines l WHERE l.order_no = ?1 AND l.sku = inventory.sku AND l.state = 'reserved'),
    updated_at = ?2
WHERE sku IN (SELECT sku FROM order_stock_lines WHERE order_no = ?1 AND state = 'reserved') AND G;   -- CHECK inv_reserved_nonneg 兜底

INSERT INTO inventory_movements (sku, type, d_reserved, available_after, reserved_after, incoming_after, damaged_after, ref_order_no, actor, created_at)
SELECT i.sku, 'ship', -l.qty, i.available, i.reserved, i.incoming, i.damaged, ?1, ?3, ?2
FROM order_stock_lines l JOIN inventory i ON i.sku = l.sku
WHERE l.order_no = ?1 AND l.state = 'reserved' AND G;

UPDATE order_stock_lines SET state = 'shipped', updated_at = ?2 WHERE order_no = ?1 AND state = 'reserved' AND G;

UPDATE orders SET status = 'shipped', status_updated_at = ?2 WHERE order_no = ?1 AND status = ?4;
```

- **触发条件只看订单状态，与 shipments 记录无关。** `0012_shipments.sql` 第 3 行写明 shipment 状态独立，不驱动 orders.status；`functions/api/admin/shipments.js` 也不改订单状态。
- `shipped → in_transit → delivered`、`in_transit → shipped`：这些订单的行状态已经是 `shipped`，守卫 `state='reserved'` 不成立，不会重复扣减。
- CHECK `inv_reserved_nonneg` 理论上不会触发，因为不变量保证 reserved ≥ 行数量之和。万一触发，说明数据不一致：整批回滚，订单不改状态，返回 500 "Inventory is inconsistent for this order — run reconciliation"，并记日志。

### 2.4 发货回退（`shipped → processing`，`order-status.js` `TRANSITIONS.shipped` 允许这一步）

- 与 §2.3 镜像：`reserved += qty`，行状态 `shipped → reserved`，流水类型 `unship`，守卫 `status = 'shipped'`。
- 这样回退之后再取消，能正确释放库存。业务含义是"货其实没出仓或已退回货架"，需用户确认（§8 Q2）。
- 状态效果的判定集中在一个纯函数里，`_lib/inventory.js` `invStockEffect(from, to)`，基于 `DISPATCHED_STATUSES`：
  - 未发出且不是 cancelled → `cancelled`：`release`
  - 未发出 → 已发出（`shipped`）：`ship`
  - 已发出 → 未发出且不是 cancelled（`processing`）：`unship`
  - 其他（`pending↔processing`、已发出状态之间互转、旧状态）：`null`，什么也不做

### 2.5 后台库存操作（新端点 §4，每个都是"UPDATE + INSERT 流水"两条语句一个 batch）

`?1 sku`，`?2 N(>0)`，`?3 now`。流水的 `reason` 必填，`actor = 'admin:<username>'`。

| op | 含义 | UPDATE |
|---|---|---|
| `incoming` | 登记补货在路上 | `SET incoming = incoming + ?2` |
| `receive` | 补货到仓 | `SET incoming = incoming - ?2, available = available + ?2`（N 超过在途数时 CHECK `inv_incoming_nonneg` → 400 "only X incoming"） |
| `adjust` | 手工增减（bucket ∈ available / incoming / damaged，delta 可正可负） | `SET <bucket> = <bucket> + ?2`（CHECK 防止变负） |
| `stocktake` | 盘点：输入实物在库数 P（含已预留未发和残次） | `SET available = ?2 - reserved - damaged` → P < reserved+damaged 时 CHECK 报错 → 400 "Count is lower than reserved + damaged"。用当下的 reserved 计算，所以盘点期间来了新订单也不会算错 |
| `damage` (from=available) | 可售件发现残次 | `SET available = available - ?2, damaged = damaged + ?2` |
| `damage` (from=reserved) | 已预留件发现残次：从可售补一件给订单，订单预留不变 | 数值与上一行相同（available−N、damaged+N），流水 type 一样，reason 注明 "reserved unit replaced"。available 不够时 CHECK 报错 → 400 "Not enough available to replace the damaged reserved units; adjust the order first"。这样"可以从 reserved 转残次"的决定落地了，同时 reserved 与订单行的不变量不被破坏 |
| `repair` | 残次修好回可售 | `SET damaged = damaged - ?2, available = available + ?2` |
| `writeoff` | 残次报废出库 | `SET damaged = damaged - ?2` |
| `threshold` | 设置低库存阈值 | `SET low_stock_threshold = ?2`（NULL 表示关闭） |

流水统一写法：

```sql
INSERT INTO inventory_movements (sku, type, d_available, d_reserved, d_incoming, d_damaged,
  available_after, reserved_after, incoming_after, damaged_after, reason, actor, created_at)
SELECT sku, ?type, ?da, 0, ?di, ?dd, available, reserved, incoming, damaged, ?reason, ?actor, ?3
FROM inventory WHERE sku = ?1;
```

- `stocktake` 的 `d_available` 无法事先算出。做法是先读出旧值 `a0`，batch 里 UPDATE 加 `AND available = ?a0` 乐观锁，流水的 `d_available = 新值 − a0`。UPDATE 影响 0 行就返回 409 "changed, reload"。
- 因为乐观锁失败时 UPDATE 是 0 行、不报错，INSERT 流水也必须加同一条件，否则会写一条假流水。简单可靠的做法：`stocktake` 分两步执行，先单独 UPDATE 并检查 changes，成功后再写流水（流水只用于审计，可以接受）。或者流水 INSERT 加 `WHERE available = ?2 - reserved - damaged AND updated_at = ?3`，用本次时间戳做令牌，推荐这种。

## 6. 边界情况与数据完整性

1. **并发超卖：** 预检之后的竞争由 CHECK 约束兜底，整单回滚（§2.1）。D1 对同一个库的写入是串行执行的，同一 batch 内部不会被其他请求插入。
2. **取消已发货的订单：** 客户路径已经拒绝（`cancelRefusal` 返回 409，用的是 `DISPATCHED_STATUSES`）。后台路径中 `TRANSITIONS` 不允许 shipped/in_transit/delivered → cancelled。两条路都不改库存。
3. **编辑/删除有库存的变体**（`functions/api/admin/showcase.js`）：
   - `saveProduct`：先算出这次保存后消失的 `color_id` 和 `size`，与该商品的 `inventory` 行比对：
     - 消失的变体有 `reserved > 0` → **409 拒绝保存**："Black / M has 4 units reserved by open orders; ship or cancel them first"。
     - 只有 `available/incoming/damaged > 0` → 409，需要 body 带 `confirmStockOrphan:true` 才放行。编辑器弹确认框；放行后这些行在库存页显示为 Unlinked，可以 Relink 或 Untrack。
     - 颜色改名或改 hex 不影响，因为 id 不变。尺码改文字等于删掉旧变体、新增一个，处理同上，改完后用 Relink 迁移到新尺码。
   - `deleteProduct` / `deleteCategory`（后者会删掉分类下所有商品）：有任何 `reserved > 0` → 409；有在库数量 → 需要 confirm；否则允许，行变为 Unlinked。
   - 注意：保存操作在拒绝时不能执行 `repricePendingShowcaseOrders`，守卫要放在 UPSERT 之前。
4. **`product_skus` 颜色重建 DELETE**（`functions/api/admin/products.js` C 段：`DELETE FROM product_skus WHERE spu=?` 后重新插入，缺省颜色码会重新编号为 `C01`、`C02`……）：本设计里库存不引用 `product_skus`，所以**不会产生孤儿**，本期不需要改。如果将来商城也要计库存，这段必须先改成按 sku 差量 upsert：
   - 已存在的 sku：UPDATE 价格/颜色名；
   - 新增：INSERT；
   - 消失的：`status='inactive'`，不 DELETE；
   - 不再给颜色自动重新编号；已有 `color_code` 必须沿用；
   - 有库存或预留的 sku 禁止变成 inactive。
   - 同样适用于 `scripts/import_products_to_d1.py` 生成的全量 `DELETE`。
5. **删除订单：** 只能删 `cancelled` 的订单，而取消时已经释放，所以 `reserved` 不会悬空；`order_stock_lines` 随 CASCADE 删除。只有一种情况会出问题：取消前就不一致（例如有人在 D1 Studio 直接改了状态），对账按钮能发现（§1.5）。**禁止在 D1 Studio 里直接改 `orders.status`**，写进运维说明。
6. **负库存：** 四个桶都有 CHECK；后台 delta 操作也由 CHECK 保证；数量参数必须是正整数。
7. **开始计库存时已有未发货订单：** 这些订单没有 `order_stock_lines`，发货时不扣、取消时不放。盘点公式 `available = P − reserved − damaged` 会把它们仍在货架上的货算进可售，造成虚高。处理方式：
   - 阶段 3：`track` 时列出该商品 `pending/processing` 的订单作为警告，管理员在初始 available 里自行扣除；
   - 阶段 5（可选）：`op:'attachOpenOrders'` 为这些订单补建 reserved 行，并扣 available。
8. **部分发货：** 本期一次把整单 reserved 扣完（锁定决定：按订单状态 shipped）。多个 shipment 分批发货不分别扣，需要的话以后再说。
9. **同一商品部分变体计库存、部分不计：** 按规则允许，不计的变体不限量。后台"Track a product"默认勾选全部组合，提醒管理员一次建齐。
10. **MOQ：** `available < moq` 时实际上下不了单，前端禁用并说明（§5.2）。服务端两个检查都有：先查 MOQ，再查库存。
11. **改价重算** 只改价格，不影响库存（`showcase-order-pricing.js`）。
12. **表未建 / 迁移漏执行：** 所有读取都处理 `no such table`，当作不计库存；后台库存页显示"Run migration 0013"。

1. **编号：** `migrations/0013_inventory.sql`。现有最大编号是 0012；`0010_price_backup.sql` 与 `0010_showcase.sql` 编号重复，且未被 git 跟踪（`git status` 显示 `?? migrations/0010_price_backup.sql`）。
2. **执行方式：** 把文件内容粘贴到 Cloudflare D1 Studio（控制台）手动执行。**不要用 `wrangler d1 migrations apply --remote`**，它会把未跟踪的 `0010_price_backup.sql`（`ALTER TABLE product_skus ADD COLUMN original_price ...`）一起执行，可能报重复列错误，或者给生产库加上意料之外的列。DDL 全部是 `IF NOT EXISTS`，重复执行是安全的。无法从仓库核实生产库 `d1_migrations` 表的当前记录，以及 0011/0012 当初是怎样执行的。
3. **绑定：** 只用现有的 `DB`（`wrangler.toml` `[[d1_databases]] binding = "DB"`），不需要新的环境变量或绑定。
4. **上线顺序与回填：**
   - 先执行 0013 → 部署主仓 functions + admin 页面 → 部署 showcase 前端。
   - 顺序反过来也安全：缺表时当作不计库存。
   - 现有 Showcase SKU 一律从"不计库存"开始，直到管理员在库存页对它执行 Track。所以第一天什么都不会坏。
   - 回滚：撤掉代码即可；表留着不影响。
5. **验证**（仓库里没有测试框架：没有 `*.test.*`，`showcase/package.json` 和 `product-showcase/package.json` 都没有 `test` 脚本）：
   - 语法检查：`node --check` 改动的 `.js`；
   - 前端：`showcase` 跑 `npm run build && npm run lint`；
   - 本地端到端：`npx wrangler d1 execute <db> --local --file migrations/0013_inventory.sql` + `npx wrangler pages dev`，手工测：下单预留、缺货 409、并发（用 `Promise.all` 同时发 N 个 POST，验证不超卖、余额不为负）、客户取消、后台 shipped/回退/取消、对账为空；
   - **确认 CHECK 报错文本里有约束名**（§1.4）；
   - `_lib/inventory.js` 的纯函数（`invStockEffect`、`invResolveLines`）可以用 Node 自带的 `node:test` 写单元测试，不需要装依赖。
