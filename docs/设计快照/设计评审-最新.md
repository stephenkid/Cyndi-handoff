# Design review: custom redemption portal (revision 4)

Document: `.kiro/reports/redemption-design.md` (969 lines). Reviewed against the repo at HEAD (6dd7c25).

**Verdict: CHANGES_REQUESTED** (3 MEDIUM, 0 HIGH, 9 NIT).

All nine open points are resolved in the document: order representation (D1), structured address (D2/5.5), link format and rate limiting (D4/D5/10.2), item pool and limits (D6), single vs multi submission (D7), admin UI (9), verbiage storage (D9), roles (11) and public data exposure (6.2, AC13, AC16, AC26). The problems below are defects in the specified mechanisms, not missing decisions.

## Findings

### 1. MEDIUM: `saveProduct` bind numbering is wrong in every case except one (8.5, `saveProduct` row)
The design makes `client_id` `?26` and adds `AND (... client_id IS ?26 OR ... IS NULL)` to `lock`. In `functions/api/admin/showcase.js` (lines 288-330) the statement binds 22 values plus `...lockBinds`, and `lockBinds` has 0 entries for a new product, 2 for an existing product without `invRows`, and 3 with `invRows` (`?25` exists only in that last case). A fixed `?26` therefore refers to a parameter index that has no bound value in two of three cases. D1 rejects the statement, so every product save by Cyndi admin would fail.
**Fix:** put `client_id` at `?23` in the VALUES list and push it as the 23rd bind, then number the lock terms after it (`?24` colors, `?25` sizes, `?26` fingerprint only when `invRows`). The lock term then reads `AND (showcase_products.client_id IS ?23 OR showcase_products.client_id IS NULL)`. Add a unit test for all three bind shapes (new, existing, existing with `invRows`) that asserts the highest `?N` equals `binds.length`.

### 2. MEDIUM: `sendEmails` claim is not unique per call, so AC19 ("never send the same row twice") can fail (7.4 step 1)
The claim is `UPDATE ... SET sending_at = ?now ...` followed by `SELECT ... WHERE sending_at = ?now`. `?now` is an ISO timestamp with millisecond resolution. Two concurrent calls in the same millisecond, or one call with a clock that does not advance between retries, read each other's claimed rows back and both send them. Selecting "the next 10 eligible rows" without `codeIds` is also not shown as one atomic statement.
**Fix:** add a `claim_id TEXT` column to `redemption_codes` (random 16 bytes per call) and write `UPDATE redemption_codes SET email_status='sending', sending_at=?now, claim_id=?claim, send_count=send_count+1 WHERE id IN (SELECT id FROM redemption_codes WHERE client_id=?c AND portal_id=?p AND status='active' AND (email_status IN ('not_sent','failed') OR (email_status='sending' AND sending_at < ?cutoff)) [AND id IN (<codeIds>)] ORDER BY id LIMIT 10) RETURNING id, name, email, token, send_count`. D1 supports `RETURNING`. Update every later write in step 3 to include `AND claim_id = ?claim`. Add a test with two simulated claims at the same timestamp.

### 3. MEDIUM: 2.2 and 8.2 contradict each other on null scope for writes
2.2: "`scope.clientId === null` is allowed only in read paths used by Cyndi admin. Every write function throws if `scope.clientId` is not a positive integer." 8.2: `admin/orders.js` becomes a thin route calling `orders-admin.js` with `scope = {clientId: null}`, including `ordChangeStatus`, which is a write. Followed literally, Cyndi admin could not change any order status after the refactor, or the implementer drops the throw and loses the safety rule.
**Fix:** state the rule once. Suggested wording: "A scope is `{clientId: <positive int>}` or `{all: true}`. Only functions in `orders-admin.js` and `inventory-admin.js` accept `{all:true}`, and only the Cyndi route files construct it. `redemption-admin.js` and everything under `functions/api/showcase-admin/` throw on anything but a positive integer. `requireShowcaseAdmin` never returns `{all:true}`." Add this to the scope lint test (the Showcase admin route files must not contain the literal `all: true`).

### 4. NIT: test 3 expects 403 for a disabled customer, 2.1 gives 401
`readCustomerSession` (customer-auth.js:309-316) returns `customer: null` for a non-active account, so 2.1 step 2 returns 401. Test 3 and AC3 say 403 for "disable the customer". **Fix:** say 401 for a disabled customer and 403 for the other three cases.

### 5. NIT: wrong line references
5.4 says `invSkuCode` de-duplicates "with `LIKE` (admin/inventory.js:387)". The `taken` preload is at lines 454-457 (`opTrack`); line 387 is variant validation. The customer cookie `SameSite=Lax` is at customer-auth.js:323, not 321. **Fix:** correct both.

### 6. NIT: `mail-day` counter increments by N, `rdmThrottleHit` increments by 1 (7.4, 10.2)
7.4 says the daily limit is "incremented for the number of claimed rows". **Fix:** give `rdmThrottleHit(db, key, windowSecs, limit, by = 1)` a `by` argument and say that when `count + by > limit` nothing is claimed and the response is 429.

### 7. NIT: Fei and Megan's accounts are not named
The user supplied both admins' email addresses (omitted from this copy). The design (A1, 15.2 step 7) says "Fei's and Megan's own accounts" without saying how the first password is set. **Fix:** name both accounts in 15.2 step 7 and say whether Cyndi sets a temporary password on the Customers page or the user does.

### 8. NIT: media endpoint omits base64 decoding (6.2a step 4)
`showcase_media.image_data` is base64 text (`upload.js:42-44`, decoded with `atob` in `showcase/media.js:17-18`). **Fix:** state that the handler decodes `image_data` the same way, and reuse that code from a shared helper so the two endpoints cannot diverge.

### 9. NIT: soft-cap overshoot reasoning (5.5)
The overshoot of `max_total_orders` is bounded by in-flight requests, not by the 60/hour `portal-submit` limit. Also `updatePortal` takes "the same fields" as `createPortal`, which includes `type`, while 9.1 says type is locked. **Fix:** reword the cap justification, and state that `updatePortal` rejects any `type` value that differs from the stored one with 400.

### 10. NIT: root `_worker.js` queries the catalog unscoped
`_worker.js` (repo root, line 252-275) serves `/api/showcase` from `showcase_products`, `showcase_categories` and `showcase_meta` with no client filter. It is outside `pages_build_output_dir` (`product-showcase/dist`), so it is likely inert, but 3 does not say so. **Fix:** add one line to section 3 confirming it is dead code and not in the scoped-query list.

### 11. NIT: Showcase admin inventory detail exposes Cyndi staff data (8.4)
Movements carry `actor` (`admin:<username>`) and free-text `reason` written by Cyndi staff. **Fix:** in the Showcase admin serializer return type, quantities and timestamp only, and replace `actor` with "Cyndi" and omit `reason`.

### 12. NIT: `orders.item_count` not specified for `RDM-` rows (5.6)
`orders.item_count` is NOT NULL and `prepareInsertOrder` requires `itemCount`. **Fix:** "sum of line quantities".

## Verified assumptions
- `isValidOrderNo` duplicates exist at admin/orders.js:22-23 (used at 136 and 342), admin/shipments.js:24 (used at 68, 101) and admin/shipments/upload.js:16 (used at 49). All reject `RDM-`.
- `prepareInsertOrder` hardcodes `'pending'` and has no `clientId` (orders.js:79-101). `order-status.js` has no `awaiting_approval`; `TRANSITIONS` and `allowedNext` behave as the design assumes.
- `invResolveOrderLines` tests `colorIndex === null` and `size === null`, returns `shortages` rather than an error, and yields `lineSkus` entries of `null` for untracked variants (inventory.js:200-260).
- `invReserveStatements` and `invTransitionStatements` match the described guard shape (`o.status = ?4`, `guardBinds`); the order UPDATE last as optimistic lock matches admin/orders.js:365-395.
- `invStockEffect` gives `release` for `pending`/`processing` to `cancelled`, so the cancel path described in 8.5 is correct.
- `invClassifyError` strings (`inv_available_nonneg`, `UNIQUE constraint failed: orders.order_no`) exist.
- `hasShowcaseAccess` checks client status; `loadCustomerById` returns `client_status` and `client_id`; `requireShowcaseAdmin` step 3 can use it as written.
- Customer and admin tokens use different `aud` values (customer-auth.js:298, auth.js:129) and the customer cookie is `SameSite=Lax`.
- `inventory`, `order_stock_lines`, `inventory_movements` schemas (0013): no `client_id`, `sku` primary key, `UNIQUE (product_id, color_id, size)`, `inventory_movements.sku NOT NULL` (so the tripwire in 8.7 fails as intended).
- `ivrResetFromOrder` is at admin/inventory.js:571 with `IVR_ORDER_RE = /^SHOWCASE-\d{8}-\d{3,}$/` at 567, and `ivwListStockSkus` at 206, both unscoped, as 8.7 describes. `listProducts` returns `skus` at line 197.
- Media upload stores `/api/showcase/media?id=<uuid>` (upload.js:46); the stored colour shape and the login gate on `/api/showcase/media` match 6.2a.
- Admin pages in `product-showcase/public/admin/`: 7 files. `showcase/` is a separate git repo using a `view` state in `App.jsx`, with `lint` and `build` scripts. `showcase-order-pricing.js` is limited to `SC-`/`SHOWCASE-` rows, so `RDM-` orders are not repriced.
- `functions/api/showcase/orders.js` guards customer cancel on `customer_id`, so `RDM-` orders (NULL customer) are unreachable there; `api/orders.js` and `orders/mine.js` already 404 for `RDM-`.
- No `functions/r/`, `_headers`, `_redirects`, mail or rate-limit code exists.

- Wrong: the `sending_at = ?now` read-back identifies one call's rows (finding 2).
- Wrong: disabled customer gives 403 (finding 4).
- Wrong line references (finding 5).
