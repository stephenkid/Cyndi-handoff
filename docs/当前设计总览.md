## 1. 平台是什么，今天线上有什么

Cyndi Global 给企业客户（第一个客户是 Hudson River Trading，简称 HRT）做定制周边（swag）。平台让 Cyndi 的员工管商品、订单、库存和物流，让客户员工在自己的选品站下单，以后还会让客户给外部人员发"兑换链接"。

已上线的功能：

| 功能 | 说明 |
|---|---|
| 公开商城 | `shop.html`，订单号 `SW-` |
| Showcase 下单 | 客户专属选品站 `/showcase/`，订单号 `SHOWCASE-YYYYMMDD-NNN`（兼容旧 `SC-`），写进共享的 `orders` 表 |
| 后台 Orders | `/admin/orders.html`，列表、筛选、改状态 |
| 物流跟踪 | 迁移 `0012`，后台在订单里管理物流单、轨迹、照片 |
| 客户取消订单 | 未发货（`pending`/`processing`）时客户可自己取消 |
| 库存第一阶段 | 迁移 `0013`，广州仓按颜色×尺码计数，下单预留、取消释放、发货扣减。负责人已在线上 D1 执行 `0013` |
| 客户物流查询页 | `/api/tracking`，燕文（Yanwen，物流承运商）运单号实时查询，凭证放在环境变量 `YANWEN_AUTH_CODE`，只在服务端使用 |
| 新客户 Portal | 另一位贡献者（Georgia Zhu）在 11-24 到 11-26 推送：登录、公开注册、忘记密码、Dashboard、项目三阶段流程，并已和 Showcase 统一登录 |

还没做的：Showcase admin（客户管理员后台）、多客户隔离、兑换门户。三者都只有设计。

| 账户系统 | 表 | Cookie | 谁用 | 能进的 API |

## 4. 多客户模型

现状：`clients` 表已存在（`0011`），HRT 是第一行。`customers.client_id` 已有。商品、订单、库存还没有 `client_id`。

已决定：

| 项 | 决定 |
|---|---|
| 商品目录 | 按客户分。`showcase_products`、`showcase_categories` 加 `client_id`，全部回填 HRT |
| 订单 | `orders` 加 `client_id`。Showcase 订单回填 HRT；商城 `SW-` 订单留空 |
| 库存 | 按客户分，但**不加列**：商品属于一个客户，库存通过商品关联到客户（设计第 5.4 节）。另一个方案是给 `inventory` 加列，待拍板 |
| 目录设置 | 单行的 `showcase_meta` 改成每客户一行的 `showcase_meta_client` |
| 兑换 | 五张新表都带 `client_id` |
| 品牌外观 | 推迟，不做 |
| 新建客户 | 不做向导，用 SQL |

**新冲突（11-25 的 fbec780，设计未覆盖）**：Portal 作者加了"客户选品池" `client_showcase_pools`，按**单个客户账户**（`customer_id`）而不是按公司过滤 Showcase 目录。没有池的账户看全部目录。这和我们"按公司分目录"是两套模型，需要定下来怎么叠加（建议：公司目录是边界，个人选品池只在公司目录里再筛一次）。另外选品池只过滤目录列表，**不过滤下单**：下单接口不检查选品池。

## 5. 库存

四个数量桶：

| 桶 | 含义 | 谁改 |
|---|---|---|
| Available 可售 | 能下单的数量 | 管理员手动（Set / Adjust） |
| Reserved 已预留 | 已下单未发货 | 系统自动 |
| Incoming 在途 | 补货在路上 | 第二阶段 |
| Damaged 残次 | 不能卖 | 第二阶段 |

预留模型：下单时 available 减、reserved 加；取消时退回；发货时从 reserved 扣出。超过 available 就拒单。只有"开启跟踪"的颜色×尺码才计库存，其余照旧按单生产。每次变动写一条流水 `inventory_movements`。

第二阶段（backlog）：在途和到货、残次处理、低库存邮件、停止跟踪、整仓盘点、出货报表、列表分页（现在最多 500 个商品）、仓库角色和审计。

**三个未审过的库存提交**（c3c3943、28a7a6f、44f6370，作者 "Cyndi Global"，11-13）。状态：**暂时保留，负责人正在问作者要不要留**。兑换功能不依赖它们。

| 提交内容 | 问题 | 设计给的处理 |
|---|---|---|
| `resetFromOrder`：清空库存后按一张订单重建 | 三条 `DELETE` 不带条件，会清掉**所有客户**的库存、流水和预留，包括等待审批的兑换订单的预留 | 改成只清指定客户；有其他订单的未结预留时拒绝；只限 Cyndi owner |
| 平铺 SKU 列表 `ivwListStockSkus` | 不按客户过滤，接入多客户后会泄露别家库存 | 移进共享库，按客户内连接过滤 |
| 用订单当期初库存的思路 | 兑换订单（`RDM-`）不能当来源 | 保留只认 `SHOWCASE-` 的校验 |

## 6. 兑换门户（设计中）

两种类型：

| | A 型"个人链接" | B 型"公开链接" |
|---|---|---|
| 链接 | 每人一个，由系统发邮件 | 全体共用一个，客户自己分发 |
| 审批 | 不用，直接进 `pending` | 每单都要客户管理员批准（`awaiting_approval`） |
| 次数 | 每个链接一张有效订单 | 每个邮箱一张有效订单 |
| 拒绝 | 不适用（可取消） | 订单取消，预留退回 |

共同规则：
- 每个商品有数量上限（例如 1），或"不限"（实际上限 100）。两种类型一样。
- 提交时立即预留库存；B 型被拒绝或订单取消时释放；发货时照常扣减。没开库存跟踪的变体不能兑换。
- 订单进共享的 `orders` 表，前缀 `RDM-`，金额为 0，收货地址存在 `redemption_claims`。Cyndi 在原 Orders 和 Shipments 页发货。
- 邮件用 Resend，复用 Portal 已有的 `functions/_lib/mailer.js`（加一个通用发信函数），发件人 `REDEEM_MAIL_FROM` 可回退到 `EMAIL_FROM`。和 Portal 共用同一个 Resend 配额。每客户每天默认最多 500 封。
- 防滥用：`redemption_throttle` 表按 IP 计数（例如每 IP 每小时 20 次提交，猜错链接 10 次/10 分钟后封）；B 型必须过 Cloudflare Turnstile 验证码；软上限默认 200 单。这张限流表也计划给 Portal 的验证码接口用。
- Cyndi admin 只有一个只读的全局兑换页，不代客户审批。

## 8. 风险和已知问题（按严重程度排）

本表只写问题和修法方向，不写利用方式。

| # | 问题 | 严重 | 来源 |
